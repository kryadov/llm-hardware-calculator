# LLM Hardware Calculator — дизайн

Дата: 2026-08-04
Статус: утверждён, готов к планированию реализации

## 1. Задача

Интерактивный калькулятор аппаратных требований для self-hosted инференса open-weights
моделей (Kimi, GLM, DeepSeek, Qwen, MiniMax). Пользователь описывает задачу — модель,
профиль нагрузки, число пользователей, SLA — и получает ранжированный список
конфигураций серверов с оценкой производительности, стоимости и готовой командой запуска.

Публикуется как статический сайт на GitHub Pages.

### Аудитория

Инфраструктурный инженер, который реально будет закупать или арендовать железо.
Отсюда следует глубина расчёта: полная модель памяти (веса × квантование, KV-cache ×
контекст × конкурентность, активации, оверхед), roofline-модель производительности,
проверка требований к интерконнекту.

### Критерии успеха

1. Ответ на вопрос «что купить», а не только «влезет ли вот это».
2. Каждое число проверяемо: формулы раскрываются с подставленными значениями
   пользователя, гиперпараметры моделей ссылаются на `config.json` на HuggingFace.
3. Отвергнутые конфигурации показываются с машиночитаемой причиной отказа.
4. Расчёт синхронный — результат меняется в том же кадре, что и ввод.
5. Инструмент переживает выход новых моделей за счёт режима ручного ввода.

### Явно вне скоупа первой версии

- Disaggregated prefill/decode (раздельные пулы под префилл и декодинг).
  Дало бы точность на больших инсталляциях, но удваивает сложность solver'а.
- Обучение и файнтюнинг — только инференс.
- Мультимодальные модели (vision/audio энкодеры).
- Живое подтягивание цен или данных моделей из сети в рантайме.

## 2. Архитектура

Ядро — чистый TypeScript без зависимостей от React. Формулы должны быть тестируемы
в изоляции и переносимы (вызов из Node без браузера).

```
src/
  core/                    чистый TS, ноль зависимостей, покрыт юнит-тестами
    units.ts               branded-типы: Bytes, Gib, Tflops, GbPerSec, TokensPerSec
    types.ts               ModelSpec, AcceleratorSpec, Workload, Deployment, Verdict
    memory.ts              веса, KV-cache, активации, оверхед фреймворка
    throughput.ts          roofline: prefill (compute-bound) / decode (memory-bound)
    workload.ts            профиль × DAU → RPS, конкурентность, длины контекста
    parallelism.ts         допустимые (TP, PP, EP); проверка интерконнекта
    solver.ts              перебор → отсев с причиной → ранжирование
    cost.ts                CAPEX, OPEX, электричество, TCO, $/1M токенов
    launch.ts              генерация команд vLLM / SGLang
  data/                    каталоги как JSON + Zod-схема + тест валидности
    models.json            гиперпараметры + verifiedAt + sourceUrl
    accelerators.json      HBM, BW, FLOPS, TDP, интерконнект, лимит GPU в узле
    pricing.json           цены, отдельным файлом с одной датой на файл
    profiles.json          сценарии нагрузки
    coefficients.json      MFU/MBU на пару «семейство железа × фреймворк»
  ui/                      React, тонкий слой над core
    App.tsx, panels/, results/, i18n/
```

Границы модулей проверяемы: `memory.ts` не знает про цены, `cost.ts` не знает про
формулы производительности, `solver.ts` не знает про React.

### Поток данных

Однонаправленный, без стейт-менеджера — всё выводится из состояния формы.

```
форма → Workload ─┐
ModelSpec ────────┼→ solver.enumerate() → Candidate[]
Accelerator[] ────┘         │
                            ├→ memory.fits()       → отсев «не влезает»
                            ├→ throughput.eval()   → отсев «не бьёт SLA»
                            ├→ parallelism.check() → отсев «нет NVLink/IB»
                            └→ cost.estimate()     → ранжирование
                                     ↓
                        Deployment[] + Rejection[] (с причиной)
```

### Два ключевых архитектурных решения

**Отвергнутые кандидаты — часть результата.** Solver возвращает не только выживших,
но и список отсеянных с машиночитаемой причиной вида `{ reason: 'oom', deficitGb: 218 }`.
UI показывает их в свёрнутом блоке. Это объясняет, почему нельзя дешевле, — половина
ценности инструмента.

**Режим Verify — тот же solver с закреплённым кандидатом.**
`solve(workload, { pin: { accelerator, count, quant } })` вместо перебора. Одна функция,
два входа, никакой параллельной ветки логики. Вкладка Explore отвечает «что купить»,
вкладка Verify — «у меня есть вот это железо, потяну ли».

## 3. Математическое ядро

### 3.1 Память

**Веса.** Эффективная битность считается с учётом scale/zero-point, иначе расчёт
квантованных чекпоинтов занижен:

```
effBits     = baseBits + (scaleBits + zeroBits) / groupSize
weightBytes = totalParams × effBits / 8
```

Для INT4 с группой 128: `4 + (16 + 4)/128 ≈ 4.16` бит, а не 4.

Для MoE в память идут **все** параметры, в вычисления — только активные
(Kimi K2: 1T всего / 32B активных; DeepSeek V3.x: 671B / 37B). Расхождение в 20-30 раз —
причина, по которой такие модели вообще хостятся.

**KV-cache** зависит от типа внимания, а не от размера модели:

```
GQA/MHA:  bytes/tok = 2 × layers × kvHeads × headDim × kvBytes
MLA:      bytes/tok = layers × (kvLoraRank + qkRopeDim) × kvBytes    // без ×2, латент один
Hybrid:   bytes/tok = fullAttnLayers × (GQA-формула) + linearLayers × constState
```

Распределение по семействам: DeepSeek и Kimi — MLA; Qwen3 и GLM — GQA;
MiniMax M1/M2 — гибрид с линейным вниманием. Квантование кэша (fp16 / fp8 / int4)
задаётся отдельно от квантования весов.

Две неинтуитивные поправки, обе моделируются явно:

- **Репликация KV при `TP > kvHeads`**: `kvReplication = max(1, TP / kvHeads)`.
  Qwen3 с 4 KV-головами на TP=8 держит кэш вдвое дороже, чем «по формуле».
- **MLA-латент при TP не шардится** в текущих реализациях — реплицируется по всем
  рангам. Управляется флагом `attention.shardedByTp` в каталоге моделей.

**Оверхед.** Фиксированные 2-3 ГБ на GPU (контекст CUDA, графы, фрагментация) плюс
буферы активаций, пропорциональные бюджету chunked-prefill, а не полной длине промпта.

**Итоговая проверка и обратный ход к конкурентности:**

```
N          = TP × PP                           // GPU в одной реплике модели
avgSeqLen  = promptTok + outputTok             // средняя занимаемая длина кэша
perGpu     = weights/N + kvPerGpu + overhead
available  = hbmPerGpu × gpuMemUtil            // дефолт 0.90
kvBudget   = (available − weights/N − overhead) × N
maxConcurrentSeqs = kvBudget / (kvBytesPerTok × avgSeqLen)
```

Конфигурация проходит проверку памяти, если `weights/N + overhead < available` и
`maxConcurrentSeqs ≥ 1`. Иначе — отказ с причиной `oom` и указанием дефицита.

`maxConcurrentSeqs` — величина, в которую упирается число пользователей. Вопрос не
«влезла ли модель», а «сколько сессий поместилось рядом с ней».

### 3.2 Производительность

Декодинг упирается в пропускную способность памяти, префилл — в вычисления.
Считаются раздельно, сводятся через утилизацию.

```
batch = min(maxConcurrentSeqs, пиковая конкурентность из профиля нагрузки)

Decode (memory-bound):
  stepBytes    = activeParamBytes/N + batch × kvBytesPerTok × avgSeqLen / N
  stepTime     = stepBytes / (hbmBw × MBU) + commTime(TP, interconnect)
  perUserTps   = 1 / stepTime                     // скорость одного пользователя
  decodeCapacity = batch / stepTime               // токенов/с на всю реплику

Prefill (compute-bound):
  flops = 2 × activeParams × promptTok + 2 × layers × heads × headDim × promptTok²
  prefillTime    = flops / (peakFlops(dtype) × MFU × N)
  prefillCapacity = promptTok / prefillTime       // токенов/с на всю реплику
  TTFT  = prefillTime + ожидание в очереди
```

`decodeCapacity` и `prefillCapacity` — пропускная способность **одной реплики** модели
(группы из `N = TP × PP` ускорителей). Обе используются в сведении ниже.

`commTime` — all-reduce на слой. На NVLink пренебрежим; на PCIe при TP=8 съедает больше
половины шага. Это причина, по которой 8× RTX в PCIe-корпусе не выдают того, что обещает
арифметика по пропускной способности.

**Сведение через утилизацию** вместо гадания, как префилл и декодинг делят GPU:

```
prefillLoad = RPS × promptTok × (1 − prefixCacheHitRate) / prefillCapacity
decodeLoad  = RPS × outputTok / decodeCapacity
replicas    = ceil((prefillLoad + decodeLoad) / 0.8)      // 0.8 — запас на хвосты
totalGpus   = N × replicas                                // итоговое число ускорителей
```

**Критерии прохождения.** Проверяются три независимых условия: `perUserTps ≥ slaTps`,
`TTFT ≤ slaTtft`, `prefillLoad + decodeLoad < 1` при `replicas = 1`. Реакция зависит от
величины промаха:

- все три выполнены → кандидат попадает в основную выдачу;
- промах по `perUserTps` или `TTFT` в пределах 20% от SLA → кандидат остаётся в основной
  выдаче, но помечается предупреждением с указанием, какое условие не дотянуто;
- промах больше 20% → кандидат уходит в блок «Не подошло» с причиной
  `slaTps` или `slaTtft` и фактическим значением.

Порог 20% нужен потому, что точность самой модели ±25%: прятать конфигурацию,
промахнувшуюся на 10%, было бы ложной точностью.

**Prefix caching** — явный параметр, а не скрытая константа. Для кодового агента,
где системный промпт и файлы повторяются, хит-рейт 0.7+ снижает нагрузку префилла втрое.
Дефолт задаётся профилем нагрузки, правится вручную.

**Спекулятивный декодинг / MTP** — опциональный тумблер с множителем 1.5–1.8× и
пометкой «зависит от acceptance rate на вашем трафике». По умолчанию выключен.

### 3.3 Коэффициенты эффективности

MFU/MBU лежат в `coefficients.json` на пару «семейство железа × фреймворк», не константой
в коде. Стартовые значения:

| Железо + фреймворк           | MBU (decode) | MFU (prefill) |
|------------------------------|--------------|---------------|
| H100/H200/B200 + vLLM        | 0.70         | 0.45          |
| MI300X/MI325X + vLLM         | 0.60         | 0.35          |
| RTX (PCIe, без NVLink)       | 0.55         | 0.30          |
| Ascend 910B / Cambricon      | 0.45         | 0.22          |

Заниженные коэффициенты у китайских ускорителей отражают состояние ядер, а не
предвзятость: инструмент обязан это показывать, иначе врёт в пользу «дешёвого» варианта.
Каждое значение снабжено источником и датой.

Результаты выдаются **диапазоном ±25%**, а не точкой.

### 3.4 Параллелизм и интерконнект

Правила отсева, каждое со своей причиной отказа:

- TP только внутри узла (NVLink / xGMI / HCCS). TP через сеть допускается лишь при
  IB ≥ 400 Gb/s и помечается как деградация.
- Модель не влезла в узел → PP между узлами (активации мелкие, работает по Ethernet)
  либо EP для MoE (требует IB).
- TP ограничен делителями `kvHeads` и числом GPU в узле.
- PP добавляет пузыри конвейера: штраф `(PP − 1) / (microbatches + PP − 1)`.

### 3.5 Стоимость

```
CAPEX  = gpuPrice × N + шасси × узлы + сеть (IB-свитчи при multi-node)
OPEX   = аренда $/GPU-час × N   ИЛИ   TDP × N × PUE(1.3) × $/кВт·ч
TCO3y  = CAPEX + электричество × 3 года    против    облако × 3 года

utilization           = prefillLoad + decodeLoad
saturatedTokensPerSec = (prefillNeeded + decodeNeeded) × replicas / utilization
$/1M токенов          = стоимость часа / (saturatedTokensPerSec × 3600) × 1e6
```

Знаменатель — **не** `prefillCapacity + decodeCapacity`. Каждая из этих величин
измерена в предположении, что ускоритель целиком занят своей фазой, поэтому их
сумма описывает железо, которое одновременно на полной скорости делает и префилл,
и декодинг — ровно то, что модель утилизации из §3.2 исключает. Вместо этого парк
масштабируется до насыщения вдоль собственного prefill/decode-микса нагрузки: при
утилизации `u` одна реплика обслуживает весь спрос, будучи занятой на `u`, значит
насыщается на `demand / u`.

Выдаются **две** метрики, потому что одна вводит в заблуждение:

- `$/1M токенов` — промпт и ответ вместе. На промпт-тяжёлых профилях (кодовый
  агент: 12k промпта на 800 ответа) занижена в 15 раз и с прайсом API несравнима.
- `$/1M выходных токенов` — вся стоимость обслуживания, делённая только на
  выходные токены. Именно она сопоставима с прайс-листами API, где промпт и ответ
  тарифицируются раздельно.

Метрика часто переворачивает выбор: конфигурация с вдвое большим CAPEX может быть
дешевле на токен.

Цены изолированы в `pricing.json` с полем `pricesAsOf` и баннером в интерфейсе.

### 3.6 Ранжирование

Ключ сортировки выдачи зависит от выбранного режима стоимости:

| Режим | Первичный ключ | Тай-брейк |
|---|---|---|
| Аренда | `$/1M токенов` | меньше `totalGpus`, затем выше `perUserTps` |
| Купить | `TCO 3 года` | меньше `totalGpus`, затем выше `perUserTps` |
| Off | `totalGpus` | выше `perUserTps` |

Кандидаты с предупреждением по SLA всегда идут после безупречных, независимо от ключа.
Режим Off существует, чтобы калькулятор оставался полезным при устаревших ценах.

### Прогрессивное раскрытие

По умолчанию видно четыре контрола: модель, квантование, профиль нагрузки, DAU.
Профиль разворачивается в строку производных чисел — «40 запросов/день × 12k промпт ×
800 ответ, пик ×4» — которую можно перебить в Advanced: длины, пиковый коэффициент,
хит-рейт префикс-кэша, SLA по tok/s на пользователя и TTFT p95, спекулятивный декодинг,
`gpu-memory-utilization`. Правка любого поля переводит профиль в состояние «Custom»
без тихой перезаписи.

### Карточка деплоя

Свёрнутая: заголовок, четыре ключевых числа, полоса разбивки памяти.
Развёрнутая добавляет схему параллелизма и требование к интерконнекту, обвязку узла
(CPU RAM ≈ 2× HBM, NVMe под веса, сеть), сплит утилизации префилл/декод, разбор
стоимости и команду запуска с кнопкой копирования:

```bash
vllm serve deepseek-ai/DeepSeek-V3.2 \
  --tensor-parallel-size 8 --max-model-len 131072 \
  --gpu-memory-utilization 0.90 --enable-prefix-caching \
  --max-num-seqs 128 --kv-cache-dtype fp8
```

### Блок «Не подошло»

Таблица: конфигурация, причина, дефицит. «4× H100 — не хватает 218 ГБ»,
«8× RTX 5090 — 11 tok/s при SLA 25», «16× H100 через 2 узла — TP через Ethernet».
Пользователь видит не только что купить, но и почему нельзя дешевле.

### Блок «Как это посчитано»

Подставляет числа пользователя в формулы раздела 3. Инженер не примет число без вывода;
здесь он может проверить каждый шаг.

### Состояние в URL

Все входные параметры кодируются в query string, каждое изменение — `replaceState`.
Ссылка на конкретный расчёт шарится и открывается у коллеги в том же виде.

### Визуализации

Без библиотеки графиков. Разбивка памяти — flex-полоса на CSS, утилизация — метр,
кривая «GPU vs DAU» — инлайновый SVG. При вёрстке использовать skill `dataviz` для
консистентной палитры и контраста в светлой и тёмной темах.

### Пересчёт

Синхронный. Полный перебор — тысячи кандидатов на простой арифметике, доли миллисекунды.
Никаких воркеров, спиннеров и debounce.

### i18n

Плоские словари `en.ts` / `ru.ts`, типизированные по ключам EN, чтобы пропущенный
перевод ловился компилятором. Язык в URL и в `localStorage`.

```jsonc
  "family": "DeepSeek", "displayName": "DeepSeek-V3.2",
  "totalParams": 671e9, "activeParams": 37e9,
  "layers": 61, "hiddenSize": 7168, "vocabSize": 129280,
  "attention": { "type": "mla", "kvLoraRank": 512, "qkRopeHeadDim": 64,
                 "heads": 128, "shardedByTp": false },
  "moe": { "experts": 256, "topK": 8, "sharedExperts": 1, "denseLayers": 3 },
  "maxContext": 163840, "nativeDtype": "fp8",
  "sourceUrl": "https://huggingface.co/deepseek-ai/DeepSeek-V3.2/blob/main/config.json",
  "verifiedAt": "2026-08-04"
}
```

`sourceUrl` и `verifiedAt` обязательны на каждой записи; каждое число в интерфейсе
кликабельно до своего `config.json`. Гиперпараметры подтягиваются с HuggingFace при
реализации, а не воспроизводятся по памяти: ошибка в `kvHeads` меняет ответ в разы.

**Охват моделей** (~25 записей): Kimi (K2 и младшие), GLM (4.6, 4.5-Air, меньшие),
DeepSeek (V3.x, R1, distill-варианты), Qwen3 (235B-A22B вниз до 8B, включая Coder),
MiniMax (M2, M1).

**Режим Custom** — форма ввода тех же полей вручную. Каталог из 25 моделей устареет за
квартал; без ручного ввода инструмент станет мёртвым. Считается обязательным.

**Охват железа**: NVIDIA ДЦ (H100 SXM/PCIe, H200, B200, GB200, A100, L40S), AMD Instinct
(MI300X, MI325X, MI355X), потребительские (RTX 5090, RTX 6000 Ada/Blackwell),
китайские (Ascend 910B/910C, Cambricon MLU, Biren, Moore Threads, Hygon),
CPU/Apple (Ampere + DDR5, Mac Studio M3 Ultra).

Структура записи ускорителя: HBM, пропускная способность, пиковые FLOPS отдельно на
BF16/FP8/INT8, TDP, тип и скорость интерконнекта, максимум GPU в узле, поддерживаемые
фреймворки.

## 6. Тестирование

Ядро тестируется как расчётная библиотека, UI — минимально.

**Юнит-тесты (Vitest), разработка по TDD:**

- Формулы KV-cache на трёх типах внимания против чисел, посчитанных вручную из `config.json`.
- Репликация KV при `TP > kvHeads` и нешардируемый MLA-латент — отдельными кейсами,
  поскольку оба неинтуитивны.
- Инварианты solver'а: рост DAU не уменьшает число GPU; более агрессивное квантование
  не увеличивает потребность в памяти; каждый отвергнутый кандидат несёт причину;
  Explore с закреплённым кандидатом даёт то же, что Verify.
- Арифметика единиц: GiB против GB, Гбит против ГБ/с. Brand-типы ловят большинство
  ошибок на этапе компиляции, тесты добивают остальное.

**Проверка на реальности** — отдельный набор: публично известные инсталляции
(«DeepSeek V3 на 8× H200», «Qwen3-32B на 2× L40S») с ожидаемым порядком tokens/s,
допуск ±40%. Задача — отлов ошибок на порядок, а не точность.

**Тест данных**: каждая запись проходит схему, `verifiedAt` не старше порога,
`sourceUrl` синтаксически валиден.

**UI**: смоук-тест рендера и круг «состояние → URL → состояние» без потери полей.

## 7. Обработка ошибок

Отказ калькулятора — всегда ответ, а не пустой экран.

- **Нет решения ни для одного железа** — показывается ближайшая недостижимая
  конфигурация («64× B200, не хватает X») и подсказка, какой параметр ослабить:
  контекст, SLA или квантование. Инструмент всегда показывает границу возможного.
- **Битая ссылка или состояние из URL** — неизвестная модель и мусор в параметрах
  игнорируются с откатом к дефолту и ненавязчивым уведомлением. Старый шаренный линк
  не роняет страницу.
- **Внутренняя несогласуемость** (NaN, деление на ноль в вырожденной конфигурации) —
  кандидат отсеивается с причиной `internal`, остальная выдача живёт.
  Error boundary на приложении — последний рубеж.

Дисклеймер в подвале: оценка ±25-30%, не заменяет нагрузочное тестирование,
цены актуальны на указанную дату.

## 8. Деплой

Vite с `base: '/llm-hardware-calculator/'`. GitHub Actions на пуш в `main`:
тесты → typecheck → сборка → публикация через `actions/deploy-pages`.
Красные тесты блокируют деплой.

Сборка полностью статическая, без сетевых запросов в рантайме: работает офлайн,
без телеметрии, ориентир ~150 КБ gzip.

## 9. Принятые решения и их обоснование

| Решение | Обоснование |
|---|---|
| Solver-перебор, а не проверка конфигурации | Отвечает на вопрос «что купить». Режим Verify получается поверх того же движка почти бесплатно. |
| Ядро без зависимостей от React | Тестируемость в изоляции и переносимость формул. |
| Отказы — часть выдачи | Объясняют, почему нельзя дешевле; это половина ценности инструмента. |
| Утилизация вместо моделирования планировщика | Честно сводит префилл и декодинг без имитации внутренностей vLLM. |
| Диапазон ±25% вместо точки | Соответствует реальной точности аналитической модели. |
| Цены отдельным файлом | Изолирует самую скоропортящуюся часть от физики расчёта. |
| Режим Custom для моделей | Каталог устареет за квартал; без ручного ввода инструмент умрёт. |
| Без библиотеки графиков | 300 КБ ради двух полос неоправданны. |
| Состояние в URL | Шарящаяся ссылка — главный механизм возврата для публичного инструмента. |
| Без disaggregated prefill/decode | YAGNI для первой версии: удваивает сложность solver'а ради точности на крупных инсталляциях. |
